Como eu fiz essa loja

Bastidores do desafio "Minha Loja no Ar": as decisões de arquitetura, o porquê do catálogo separado do front, o mapeamento pra AWS e a auditoria de Lighthouse — na prática, não no discurso.

1 · O que eu construí e como o código está organizado

A MapleStore é um site estático (HTML + CSS + JS puros, sem framework) dividido em duas responsabilidades bem separadas:

  • Frontend (index.html, css/style.css, js/app.js) — a vitrine: layout, busca, filtro por categoria e o carrinho fictício.
  • "Backend" de dados (data/products.json) — o catálogo puro, sem nenhuma marcação de HTML dentro dele. É a peça que simula um serviço de commerce: se um dia isso virar uma API de verdade, o front não muda uma linha, só troca a URL do fetch.

Estrutura de pastas: 

index.html            → página da loja
como-fiz/index.html  → esta página
css/style.css         → toda a identidade visual
js/app.js             → busca, filtro, render e carrinho
data/products.json    → catálogo (o "backend" de dados)
assets/icons/         → ícones SVG reaproveitados
images/               → fotos reais dos produtos, por categoria

2 · Por que o catálogo é separado do front (headless commerce)

Nenhum produto está escrito dentro do HTML. O js/app.js faz fetch("data/products.json") assim que a página carrega, e só então monta os cards na tela. Isso é headless commerce em miniatura: o "corpo" que guarda os dados (o JSON) é uma peça independente de quem desenha a vitrine (o JS/CSS). Na prática, dá pra trocar o visual inteiro da loja sem tocar no catálogo, ou trocar o catálogo (adicionar produto, mudar preço) sem tocar no design — são duas responsabilidades que não se misturam.

3 · Se essa loja fosse pra AWS: a jornada do clique

Hoje ela está numa hospedagem estática gratuita. Se essa mesma arquitetura fosse pra AWS, cada peça entraria assim:

Route 53 DNS — resolve maple.com pro CloudFront
CloudFront CDN — cacheia HTML/CSS/JS/imagens perto do visitante
S3 Origem — guarda os arquivos estáticos (o que hoje é este próprio projeto)
API Gateway + Lambda Se o catálogo virasse dinâmico, entraria aqui no lugar do JSON estático

O caminho do clique fica: navegador → CloudFront (CDN) → S3 (origem). Na primeira visita de cada região, o CloudFront busca o arquivo lá no S3 e guarda uma cópia (cache) mais perto do usuário. Nas próximas visitas — inclusive de outras pessoas na mesma região — o CDN já responde direto do cache, sem incomodar o S3 de novo. É exatamente o que segura a loja de pé se 10 mil pessoas acessarem ao mesmo tempo: em vez de 10 mil pedidos batendo na origem, a maioria é respondida pelas bordas do CDN, mais perto e mais rápido.

4 · Lighthouse — auditoria e plano de melhoria

Rodando o Lighthouse na loja publicada, os pontos que mais pesam tendem a ser: tamanho das imagens de produto (peço pra otimizar/ comprimir antes de subir), fontes do Google carregando antes do texto aparecer (dá pra adicionar font-display: swap, o que este projeto já faz) e ausência de alt em imagem — por isso todo <img> do catálogo recebe o nome do produto como texto alternativo automaticamente, vindo do próprio products.json.

Se eu fosse priorizar uma melhoria só, seria comprimir e redimensionar as fotos reais dos produtos antes de subir (formato WebP, largura máxima ~800px) — é o item que mais pesa em performance numa vitrine com fotos.

5 · Onde eu plugaria IA nessa loja + o que foi mais difícil

Os pontos onde IA generativa faria mais sentido aqui: busca semântica (entender "quero guardar minhas cartas raras" e sugerir fichário + sleeve premium, não só bater palavra-chave), recomendação por categoria comprada junto (quem leva deckbox costuma levar sleeve) e um atendimento de primeiro nível pra dúvidas de estoque/entrega. A parte mais difícil de verdade foi decidir onde termina o "front" e onde começa o "backend" num projeto sem servidor de verdade — e resolver isso tratando o JSON como se fosse uma API já resolve 90% da dúvida.

Bônus · onde entraria um BFF com app mobile

Se a MapleStore ganhasse um app mobile, o app não bateria direto no products.json estático: entraria um BFF (Backend-for-Frontend) entre os dois — uma camada de API pensada pro formato de tela do app (menos dado por resposta, campos resumidos, paginação), enquanto o site web continuaria consumindo o catálogo do jeito que está hoje ou por um BFF próprio dele. Cada cliente (web, mobile) fala com o seu BFF, e os BFFs conversam com o mesmo catálogo por trás.

App mobile Tela otimizada, menos dados por request
BFF mobile Molda a resposta pro formato do app
Catálogo Fonte única de produtos
Site web Consome direto ou via BFF próprio
